Parte 9 — Pense como arquiteto
------------------------------

Qual problema arquitetural resolvemos ao adicionar persistência?
Os dados deixam de depender da memória do processo Node.js. Cadastros sobrevivem
a reinício do servidor, deploy e queda da aplicação.

Por que PostgreSQL faz sentido para a EasyFood neste momento?
É relacional, combina com entidades como Restaurant, suporta consultas futuras
(pedidos, usuários) e é padrão de mercado para evoluir de MVP para produção.

Qual é a responsabilidade do Prisma?
ORM entre Express e PostgreSQL: schema, migrations, queries tipadas
(findMany, create) sem SQL manual na rota.

O que acontece com a API se o banco ficar indisponível?
GET e POST retornam HTTP 500 com mensagem genérica; o servidor pode falhar
na inicialização se prisma.$connect() não conseguir conectar.

Que vantagens ganhamos em relação ao array em memória?
Dados duráveis, base para relacionamentos, integridade e consultas; várias
requisições compartilham o mesmo estado persistido.

Que nova complexidade foi adicionada?
PostgreSQL instalado, .env com DATABASE_URL, migrations, seed, Prisma Client
e dependência de serviço externo (banco rodando).

Quais trade-offs surgiram com essa decisão?
Mais setup e operação; falha do banco derruba a API; curva de aprendizado
Prisma/migrations vs array simples.

Nosso desenho arquitetural precisa ser atualizado?
Sim. De Cliente → Express → Array para Cliente → Express → Prisma → PostgreSQL,
registrado no ADR-002-persistencia-com-postgresql.md.
